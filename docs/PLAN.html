2. สมมติฐาน (ทุกข้อจะเขียนลง README)

ตรงไหนที่โจทย์ไม่ชัด เราเดาอย่างมีเหตุผล แล้วบันทึกไว้ว่าถ้าเดาผิดจะเปลี่ยนอะไร

idสมมติฐานถ้าผิดจะเปลี่ยนอะไร
A1mock LINE OA เป็นเส้นทางที่ใช้ให้คะแนน คนตรวจรันได้โดยไม่ต้องมีบัญชี LINE ตอนนี้เรามี OA จริงด้วย (อ่านอย่างเดียว ดู A11) ไว้เก็บหลักฐาน HAR และ OA ทดสอบฟรีไว้ลองส่ง จึงตรวจ WebClient กับของจริงได้ถ้า WebClient ไม่เสร็จ README บอกตรง ๆ และทาง mock ยังใช้ได้
A2MCP server หนึ่ง process = session ของพนักงาน CS หนึ่งคน เข้าได้หลาย OA ("bot") กำหนดใน config ได้ว่าให้เข้า OA ไหนบ้างถ้าต้องรองรับพนักงานหลายคน ต้องแยก session ต่อคน และใช้ HTTP transport
A3"แชทที่กำลังคุยอยู่" = แชทที่ยังไม่ done/resolved เรียงตามเวลาข้อความล่าสุด มีตัวกรอง unread และ allแก้แค่ตัวกรอง
A4Search ค้นแบบคำหรือบางส่วนของคำ จากข้อความ ชื่อลูกค้า และชื่อไฟล์ ต้องค้นภาษาไทยได้ client ที่เจอไม่มี endpoint ค้นข้อความ จึงค้นจาก index ในเครื่องถ้า HAR เจอ API ค้นข้อความจริง WebClient.search จะใช้ API นั้น แล้ว index เหลือหน้าที่เป็นแค่ cache
A5Agent รันในเครื่องเดียวกับพนักงาน CS (stdio)ถ้า deploy บน server ต้องใช้ Streamable HTTP และ auth ฝั่ง MCP
A6ข้อความที่ agent ส่ง ขึ้นว่าส่งโดยพนักงานที่ login อยู่ ทุกการส่งถูกบันทึกใน audit logไม่มี
A7การ mark ว่าอ่านแล้วเป็น API แยก (PUT .../markAsRead มีหลักฐานแค่ PUT) read_chat จึงไม่ mark read มี flag markRead ซึ่งปิดไว้เป็นค่าเริ่มต้นเปิด flag ถ้าทีม CS ต้องการ
A8link คนแจ้งปัญหาใน support OA ไปที่ OA ของผลิตภัณฑ์ เพราะ CS ต้องรู้บริบทการใช้งาน: สถานะบัญชี, integration ที่เชื่อมอยู่, กิจกรรมล่าสุด, ข้อความตอบกลับที่ errorถ้าไม่ link CS ต้องถามลูกค้าในสิ่งที่ระบบรู้อยู่แล้ว
A91 แชทมีหลายเคส ข้อความจากปุ่ม rich menu เปิดเคสใหม่ตามชนิดของปุ่ม และ AI เปิดเคสเพิ่มได้เมื่อลูกค้าเริ่มเรื่องใหม่โดยไม่กดปุ่มถ้า CS อยากได้ 1 แชท 1 เคส ก็แค่ไม่ใช้ open_case
A10link คนข้าม OA ด้วยอีเมลที่ลูกค้าพิมพ์ จับคู่ใน server และให้ CS ยืนยัน event ใน OA ของผลิตภัณฑ์ที่ยืนยันอีเมลนับเป็นอีเมลที่ยืนยันแล้ว การ link อัตโนมัติด้วย userId ต้องให้ทั้งสอง OA อยู่ provider เดียวกัน ซึ่งยังไม่ได้เช็กถ้าอยู่ provider เดียวกัน เพิ่มการ link ด้วย userId ทีหลังได้
A11OA จริงมีแชทของคนจริง จึงอ่านอย่างเดียว: ห้ามส่ง ห้ามกด Follow up / Resolve และห้ามเปิดแชทที่ยังไม่อ่าน (เปิดแล้วนับว่าอ่าน) ไฟล์ HAR เก็บที่ ~/lineoa-har/ นอก repo การส่งและอัปโหลดทดสอบกับ OA ทดสอบเท่านั้นไม่มี
A12AI ฝั่ง client ทำงานที่ต้องใช้ AI (เสนอแท็ก สรุป ร่างคำตอบ) server ไม่มี LLM key และไม่เรียก LLM เองถ้าให้ server เรียก LLM ต้องมี DPA และ key ใน config

6. Authentication: server ทำงานแทนพนักงาน CS ได้อย่างไร

หลักการ: คน login เอง server ถือแค่ session ไม่เคยเห็น password

  1. npm run login เปิด Chromium จริงขึ้นมา พนักงาน login เองด้วย LINE Business ID / อีเมล / QR และ 2FA หรือ captcha ถ้ามี เราจึงไม่ต้องรับมือ captcha และไม่ต้องเก็บรหัสผ่าน
  2. เก็บ cookie __Host-chat-ses, chat-device-group, XSRF-TOKEN (chat.line.biz) และ session (account.line.biz) ตรวจด้วย GET /api/v1/me และดึงรายการ OA จาก GET /api/v1/bots
  3. SessionStore เขียนลง ~/.config/lineoa-mcp/session.json สิทธิ์ 0600 อยู่นอก repo และอยู่ใน gitignore ค่าลับไม่ถูกพิมพ์ลง log หรือผลลัพธ์ของ tool
  4. WebClient แนบ cookie, refresh CSRF และจำกัด rate · 401 not_login → AUTH_EXPIRED · 403 → refresh CSRF หนึ่งครั้ง ถ้ายังไม่ได้ → FORBIDDEN · ถ้า server ส่ง Set-Cookie ใหม่มา เก็บค่าใหม่ไว้ใช้ · แนบ cookie เฉพาะ host ใน allowlist และ redact header ลับใน log (linebiz) · มี lock file กันไม่ให้ server สองตัวใช้ session เดียวกัน (telegram-mcp, LINELib)
  5. จำกัดขอบเขต: เข้าได้แค่ bot id ใน config · role ของพนักงาน (Admin / Operator / chat-only) ยังมีผลฝั่ง LINE · identity guard: ไม่ยอมเริ่มทำงานถ้า me ไม่ตรงกับ LINEOA_EXPECTED_ACCOUNT
