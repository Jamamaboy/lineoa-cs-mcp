2. ตัวที่ใกล้เราที่สุด 8 ตัว: ต่างกันตรงไหน ดีตรงไหน

เลือกจาก 23 ตัวที่ศึกษา: 4 ตัวคุยกับ chat.line.biz ตรง ๆ, 3 ตัวเป็น MCP ที่ทำงานในนามคน และ 1 ตัวเป็น MCP ทางการของระบบ helpdesk ข้อมูลจาก test/research/data/*.json

omnichat-bridge LINE · Chrome extension

บริษัทไทย (KaoJai) ดึงแชท LINE OA / Shopee ส่งเข้า server ของตัวเอง และตอบกลับผ่านแท็บที่ login อยู่

  • เข้าบัญชียังไง: ใช้ cookie ของแท็บ chat.line.biz ที่เปิดอยู่ ครอบ window.fetch ไม่ขอสิทธิ์ cookies
  • ดีตรงไหน: ใกล้โจทย์ที่สุด อ่าน ส่ง และส่งไฟล์ผ่าน endpoint ภายในได้ครบ · ยืนยันการส่งด้วย sendId · ส่งข้อมูลแบบเซ็น HMAC · มี test 995 ข้อ
  • ต่างจากเรา: ต้องเปิดแท็บค้างไว้ · ไม่ใช่ MCP เป็นสะพานไป server ของเขา · ไฟล์ขาเข้าส่งต่อแค่ URL ไม่โหลดไฟล์เอง
  • เอามาใช้: กันส่งซ้ำด้วย sendId · เกณฑ์ขนาดไฟล์ (รูป 20 MiB, ไฟล์ 32 MiB)

LINELib LINE · Python library

ไลบรารีที่ครบที่สุดฝั่ง LINE: login, อ่าน, ส่ง, อัปโหลด, SSE

  • เข้าบัญชียังไง: ใช้ cookie ที่บันทึกไว้ ถ้าไม่ได้ก็ login ด้วยอีเมล + รหัสผ่าน + OTP หรือเปิด browser ด้วย Playwright
  • ดีตรงไหน: endpoint ครบที่สุด · อัปโหลด 2 ขั้น (uploadFile → bulkSendFiles) · มี realtime ผ่าน SSE · test 150 ข้อ
  • ต่างจากเรา: รับรหัสผ่านไว้ใน process · ไม่ตรวจขนาดและชนิดไฟล์ · ส่งทุกไฟล์เป็น application/octet-stream
  • เอามาใช้: แผนที่ endpoint และ flow อัปโหลด · ไม่เอา: การเก็บรหัสผ่าน

linebiz LINE · TypeScript SDK

SDK อ่านอย่างเดียว เรียก API ภายในด้วย session cookie

  • เข้าบัญชียังไง: รับ cookie ที่ export มาจาก browser · กรองเฉพาะ *.line.biz · จัดการ CSRF
  • ดีตรงไหน: type ของ API ชัดที่สุด · ปิดบัง header ลับใน log · แยก error 401 not_login · test 241 ข้อ
  • ต่างจากเรา: ไม่มี login ไม่มีส่งข้อความหรือไฟล์ · เพิ่งเริ่มโปรเจกต์ ยังไม่มีดาว
  • เอามาใช้: type ของข้อมูล · allowlist ของ host ที่ส่ง cookie · AUTH_EXPIRED แยกจาก FORBIDDEN

propertyos-line-importer LINE · Chrome extension

ดึงประวัติแชท ผู้ติดต่อ แท็ก และโน้ตจาก LINE OA เข้า PropertyOS

  • เข้าบัญชียังไง: ใช้ cookie ของ browser ผ่าน host_permission เดียว ไม่มี content script
  • ดีตรงไหน: เจอ endpoint ที่ repo อื่นไม่มี: messages.csv, notes, tags, owners, saved replies · ขอสิทธิ์น้อยที่สุดในกลุ่ม · test 65 ข้อ
  • ต่างจากเรา: ไม่ส่งข้อความ ไม่จัดการไฟล์แนบ · ผูกกับระบบของเขา
  • เอามาใช้: เติม index ครั้งแรกด้วย messages.csv · ดึง notes / tags / ผู้รับผิดชอบมาใส่โปรไฟล์

telegram-mcp MCP ในนามคน

MCP ของ Telegram ใช้ session ของผู้ใช้จริง (ดาว ~2k)

  • เข้าบัญชียังไง: สร้าง session นอก MCP ด้วยสคริปต์ login (เบอร์ + รหัส + 2FA หรือ QR)
  • ดีตรงไหน: ตรวจว่าเป็นบัญชีที่ตั้งไว้ก่อนเริ่ม · โหมดอ่านอย่างเดียว · allowlist ของแชท · ไฟล์ลงได้เฉพาะโฟลเดอร์ที่อนุญาต · ดาวน์โหลดแบบ atomic · annotation readOnlyHint ทุก tool
  • ต่างจากเรา: มี 147 tool มากเกินไปสำหรับ agent · ส่งไฟล์นามสกุลอะไรก็ได้เป็นค่าเริ่มต้น
  • เอามาใช้: guard บัญชี · โฟลเดอร์ไฟล์ที่อนุญาต · ดาวน์โหลด atomic · lock file

slack-mcp-server MCP ในนามคน

MCP ของ Slack ใช้ token จาก browser ไม่ต้องสร้าง bot (ดาว ~1.9k)

  • เข้าบัญชียังไง: ผู้ใช้ก๊อป token xoxc + cookie xoxd จาก browser ใส่ env
  • ดีตรงไหน: ปิดการส่งเป็นค่าเริ่มต้น ต้องเปิดเองและตั้ง allowlist ของ channel · รูปส่งกลับเป็น image ให้ AI เห็น (ไม่เกิน 5 MB)
  • ต่างจากเรา: ต้องก๊อป token เอง · ไม่บอกชัดเมื่อ token หมดอายุ · cache เก็บข้อมูลผู้ใช้แบบ plaintext
  • เอามาใช้: LINEOA_ALLOW_SEND + allowlist · คืนรูปเป็น image content

whatsapp-mcp MCP ในนามคน

MCP ของ WhatsApp ส่วนตัว ผ่าน bridge ภาษา Go (ดาว ~6.8k มากที่สุดในกลุ่ม)

  • เข้าบัญชียังไง: สแกน QR ครั้งเดียว bridge ถือ session ต่อเอง
  • ดีตรงไหน: เก็บข้อความใน SQLite ในเครื่อง ค้นเร็ว · โหลดไฟล์เมื่อขอเท่านั้น คืนเป็น path · ค้นพร้อมข้อความรอบ ๆ
  • ต่างจากเรา: REST ของ bridge ไม่มี auth และเปิดทุก interface · ไม่มีการกันส่งผิด · ไม่ pin version จนติดตั้งใหม่แล้วพัง
  • เอามาใช้: index ในเครื่อง · ไฟล์แบบ on-demand · ค้นพร้อม context · ไม่เอา: REST ที่เปิดโล่ง (mock ของเรา bind แค่ 127.0.0.1)

Intercom MCP MCP ทางการ helpdesk

MCP แบบ remote ของ Intercom อ่านบทสนทนาและผู้ติดต่อ

  • เข้าบัญชียังไง: OAuth 2.0 + PKCE ผ่าน browser · มี refresh token
  • ดีตรงไหน: ขอบเขตชัด เน้นอ่าน · tool เขียนมีตัวเดียวคือโน้ตภายใน ไม่ส่งหาลูกค้าเลย
  • ต่างจากเรา: ใช้ API ทางการ · ไม่บอกวิธีจัดการไฟล์แนบ · source ปิด
  • เอามาใช้: แนวคิด "อ่านเป็นหลัก เขียนเท่าที่จำเป็น" · โน้ตภายในเป็นทางเขียนที่ปลอดภัย

5. สิ่งที่เห็นซ้ำ และจุดที่ท้าทายแผนเรา

เห็นซ้ำหลายตัว

  • login ครั้งเดียว เก็บ session ในเครื่อง tool น้อยและชัด
  • ระบบ helpdesk ใหญ่ ๆ แยก "เขียนภายใน" (โน้ต, draft) ออกจาก "ตอบลูกค้า" และเปิดอย่างหลังทีหลัง ตรงกับชั้นเคสของเรา (เขียนแค่ในเครื่อง) กับ send_message (ถึงลูกค้า)
  • error ที่บอกชนิดชัด ๆ ดีกว่าล้มเงียบ: session หมดอายุ, redirect ไปหน้า login, endpoint เปลี่ยน
  • แทบไม่มีใครจัดการไฟล์แนบดี ๆ เรื่องนี้จึงเป็นจุดขายของเรา

ท้าทายแผนเรา

  • ref ของ LINE OA ตัวเดียวที่เจอใหม่ (PicSee) คลิกหน้าเว็บ ไม่ได้เรียก API ตรง แปลว่าถ้า API ภายในเปลี่ยน การคลิกหน้าเว็บคือทางสำรองจริง · เราจะเขียนเป็นแผนสำรองใน README แต่ไม่สร้าง
  • หลายตัวเปิดแชทแล้ว mark read ให้เอง เป็นผลข้างเคียงที่คนไม่รู้ตัว เราต้องเขียนใน description ของ tool ให้ชัดว่าไม่ทำ
  • มีแค่ 3 ตัวที่กันส่งผิดจริง และใช้คนละวิธี เราควรรวมทั้ง 3 วิธี (ข้อ 6)
